========================= joinFeasibility =========================
SUMMARY: The join is highly feasible for international English sets and it is number-driven, not name-driven: PriceCharting embeds the collector number in the card name ("Umbreon VMAX #215") and URL slug ("umbreon-vmax-215"), and TCGdex's localId matches it verbatim — an actual join I executed on two sampled 150-product pages matched 283/283 numbered products (139/139 Evolving Skies vs swsh7, 144/144 Base Set vs base1) with 97% exact name agreement, the mismatches being known synonym classes (Electric/Lightning Energy, Nidoran vs Nidoran♂, Pokemon vs Pokémon). TCGdex directly supplies all three enrichment targets: cardCount.official (203 for Evolving Skies — the "/203"), localId ("215"), and dexId ([197] = Umbreon) for species. Set-level mapping is the real work: stripping the "Pokemon " prefix exact-matches only 124 of PC's 300 distinct set names against TCGdex's 218 English sets; ~20 more international sets need a one-time alias table, and the remaining ~157 (127 Japanese, 15 Chinese, 5 Korean, 10 Topps, plus Burger King/Oreo/Trick-or-Trade-style products) are largely unjoinable via the English TCGdex catalog — Japanese sets exist only in TCGdex's ja locale (177 sets) under Japanese-script names and 404 under /en. Structural quirks are all tractable with routing rules: PC folds Trainer/Galarian Gallery cards into the parent set as #TG23/#GG70 while TCGdex splits them into sibling sets (swsh9.5tg, swsh12.5gg) with identical TG##/GG## localIds; PC's one "Pokemon Promo" grab-bag maps onto 13 TCGdex promo sets routed by number prefix (SWSH262→swshp, XY124→xyp) with bare-numbered modern promos ambiguous across eras; PC lists print variants ([1st Edition], [Shadowless], [Reverse Holo], [Prize Pack]) as separate products that TCGdex models as variant flags on one card — an N:1 that is harmless for this enrichment since number, set size, and species are identical across variants.

RECOMMENDATION: Build the enrichment as a two-phase batch join inside the worker, keyed on collector number with name as a confirmation gate, and store an explicit match_status per card rather than forcing a match. Phase A (set mapping, one-time, ~300 rows, human-reviewed): (1) partition PC sets by slug prefix — japanese/chinese/korean/topps/burger-king/oreo/world-championships → status UNMAPPED, never fuzzy-matched; (2) for the rest, normalize (strip leading 'Pokemon ', casefold, accent-fold, unify '&'/'and', strip punctuation) and exact-match against TCGdex /en/sets names (measured: 124/300 hit); (3) hand-alias the ~20 stragglers (151, Pokémon GO, Rumble, McDonald's Collection YYYY, Expedition Base Set, FireRed & LeafGreen, HeartGold SoulSilver, Team Magma vs Team Aqua, Battle Academy, ...); (4) attach sibling-set routes discovered from the TCGdex list: parent set → {tg/gg gallery sibling, shiny-vault sibling}, celebrations → {cel25, cel25cc, swshp}, pokemon-promo → all 13 promo sets. Phase B (card join): parse `^(base)\s*(\[tag\])?\s*(#num)?$` from cards.name; no #num → status NO_NUMBER (sealed; exclude from denominator); normalize num (uppercase, split alpha prefix from digits, strip leading zeros); route by prefix (TG/GG/SV/CC → gallery sibling, SWSH/SM/XY/BW/DP/HGSS → promo set) else parent set; look up localId; then confirm name (accent/symbol-fold, casefold, energy-synonym table: Electric→Lightning, Dark→Darkness, Steel→Metal) — agree → CONFIRMED and write enrichment {card_number = localId, set_official_size = set.cardCount.official, species = dexId[] resolved to names, null for Trainer/Energy by category}; disagree → NAME_MISMATCH, no write, review queue. Keep the enrichment in its own table keyed by the PriceCharting product id with tcgdex_card_id + match_status + matched_at, so unmatched is a first-class state (mirroring the project's LOW DATA discipline) and re-runs are idempotent. Before committing to scope, run one SQL query against the sibling DB — card counts grouped by the slug-prefix partition — to turn the set-level 48% (≈145/303 mappable sets) into a real card-level coverage number; expect near-100% of numbered products to match within mapped sets (283/283 in this session's samples) and treat Japanese sets as a deliberate later phase with a curated 127-row alias table rather than a fuzzy matcher.

RISKS:
 - Japanese sets are the largest single bucket (127 of 303 set slugs) and cannot auto-join: TCGdex serves them only under the ja locale with Japanese-script names (en/S6a returns 404), and at least one PC Japanese card URL carries no number at all — expect this whole bucket to need a curated alias map or a different source, and until the sibling DB is queried for per-set card counts the overall card-level match rate is genuinely unknown (could be anywhere from ~45% to ~75% of 91,570 cards).
 - PC's 'Pokemon Promo' grab-bag mixes every era; bare-numbered promos (#53, #44, #85) collide across WOTC/Nintendo/DP/SV promo ranges and must be resolved by name+number across 13 TCGdex promo sets — some will remain ambiguous.
 - Celebrations Classic Collection breaks the number join outright (PC #4 vs TCGdex CC002); any set that reprints cards under original numbering needs a special case — only 25 cards here, but the pattern may recur (e.g. TCG Classic decks, which TCGdex may not carry at all).
 - Fuzzy set-name matching must hard-exclude japanese/chinese/korean slug prefixes first, or 'Pokemon Korean Scarlet & Violet 151' will happily match TCGdex '151' and silently enrich Korean cards with English-set data — a wrong-but-plausible failure the project's rules exist to prevent.
 - TCGdex has no shadowless variant concept and models 1st Edition/reverse as flags, so PC variant products all inherit the same enrichment; that is correct for number/size/species but means tcgdex_card_id is deliberately N:1 and must not be treated as unique per PC product.
 - cards.set_id in the scraper DB is never updated when a card moves sets (documented TODO), so a small fraction of joins will route through a stale set.
 - Name-agreement checking must whitelist known synonym classes (Electric/Lightning, Dark/Darkness, Steel/Metal Energy; accent folding; gender symbols; VStar/VSTAR casing) or it will flag ~2-3% false mismatches; conversely, skipping the name check entirely risks silently accepting wrong-number matches.
 - TCGdex is a community-maintained open API: coverage lag on brand-new sets (PC already lists 2026 sets like 'Pokemon Phantasmal Flames'), uptime, and rate limits are unverified — for a Pi batch worker, mirroring the per-set JSON (218 requests, cacheable) or self-hosting the dataset should be evaluated before taking a live dependency.
 - Everything measured here comes from two 150-product pages plus targeted probes; older special-numbered sets (Aquapolis H-series, crystal a/b variants — TCGdex ecard2 has 40 non-numeric localIds) were verified on the TCGdex side only, not the PC side.

========================= alternatives =========================
SUMMARY: Four credible alternatives to TCGdex exist, and they split cleanly on the three fields. The Pokemon TCG API (pokemontcg.io) is the only source that carries all three explicitly — card.number "215", set.printedTotal 203 (distinct from total 237, which includes secret rares), and nationalPokedexNumbers [197] — and its data is current through Pitch Black (2026/07/17), but its live cards endpoint failed 8 of 10 probes with 500/502 today, so the safe consumption path is its bulk GitHub mirror PokemonTCG/pokemon-tcg-data (same data, pushed 2026-07-17, contains me1–me5). TCGCSV (TCGplayer's catalog, refreshed daily ~20:00 UTC, no auth) uniquely encodes number and printed size together as extendedData Number = "215/203" and disambiguates variants by product name ("Umbreon VMAX (Alternate Art Secret)"), but has no species/dex field at all. The tcgdex/cards-database repo used directly is the freshest source (pushed 2026-08-12, all Mega Evolution sets present with dexId populated) but its files are TypeScript not JSON, and the card number lives only in the filename with inconsistent zero-padding ("215.ts" vs "001.ts"). PokeAPI carries zero TCG data but cleanly maps dex number → species name (197 → "Umbreon"), which every dexId-based source needs as a companion; Scrydex is the commercial successor ($29–$399+/mo) and not a fit for a free batch worker.

RECOMMENDATION: Best fit for the three fields is the pokemontcg.io dataset consumed as bulk JSON from the PokemonTCG/pokemon-tcg-data GitHub repo — it is the only source with all three fields explicit and cleanly separated (card.number, set.printedTotal distinct from total, nationalPokedexNumbers), it is current through the newest set, and the repo path avoids the live API's demonstrated 5xx instability and rate limits entirely; pair it with a one-time PokeAPI (or static) dex-number-to-name table for species names. Keep TCGCSV as the cross-check and variant-disambiguation source: its per-card 'Number': '215/203' strings independently confirm both number and printed denominator, and its TCGplayer product names ('Alternate Art Secret') distinguish variants that share a dex number. Treat direct consumption of tcgdex/cards-database as a fallback only — freshest data but TypeScript files and filename-encoded numbers make it the most awkward fit for a .NET batch worker (the TCGdex API, covered separately, is the better face of that same data). Ignore Scrydex/PokéWallet/PokeTrace for this use case — commercial price APIs, wrong cost model for a free enrichment pass on the Pi.

RISKS:
 - pokemontcg.io live API instability is severe right now (8/10 probes returned 500/502 on the cards endpoint while sets worked) — any design that calls it per-card at runtime will fail; only the bulk GitHub repo path is dependable, and even that could stall if maintainer energy has genuinely moved to the commercial Scrydex product (that shift is a secondhand blog claim, not verified from the team).
 - pokemon-tcg-data repo updates appear to land in bursts (pushed_at exactly on Pitch Black's release day) — a set released between pushes would be temporarily absent; pushed_at needs monitoring, not assuming.
 - No source yields the species NAME directly: pokemontcg.io and tcgdex give a dex number array (nationalPokedexNumbers / dexId) requiring a PokeAPI or static mapping, and multi-Pokemon cards return multiple dex numbers, so the schema must allow 0..n species per card.
 - TCGCSV has no species field at all — species would have to be inferred from product names, which is fuzzy; its groups also mix sealed products with cards (288 products vs 237 cards in Evolving Skies), requiring filtering by extendedData presence.
 - Using tcgdex/cards-database directly means parsing TypeScript source files from a .NET worker, and the card number exists only as the filename with era-dependent zero-padding ('215.ts' vs '001.ts') — real integration friction versus consuming JSON.
 - None of these sources carry pricecharting.com identifiers, so joining to PokemonInvestBatch's cards table is name+set string matching regardless of source — the choice of source does not remove the matching problem.
 - Field semantics diverge subtly across sources (e.g. rarity: 'Rare Rainbow' vs 'Secret Rare' for the same card), so mixing sources per-field risks silent inconsistency; pick one primary source per field and record it.
 - Keyless pokemontcg.io access (1000/day, 30/min) cannot cover 91,570 cards in one pass even when healthy; with a free key it is 20,000/day — bulk file consumption sidesteps rate limits entirely.

========================= licensingOps =========================
SUMMARY: TCGdex is the clean fit on all three axes. Licensing: its data lives in the tcgdex/cards-database repo under a plain MIT license (fetched verbatim), which expressly permits copying, modifying, merging, publishing, and even selling — permanent storage of enriched values in CardStock's Postgres is unambiguously permitted, with the only obligation being preservation of the copyright/permission notice; there is no separate data license — the repo IS the data. Operations: no API key, no published rate limits ("please be considerate... cache responses locally"), an officially supported self-host path via Dockerfile/docker-compose, and the tcgdex/server Docker image ships linux/arm64 so it runs on the Pi 5; a full English backfill is at most 218 per-set API requests, or zero if the repo is vendored/self-hosted, and a live probe confirmed one set request returns every card's number (localId), the official printed size (cardCount.official=203 vs total=237 for Evolving Skies), and the full card object carries dexId=[197] for species. pokemontcg.io: free key at dev.pokemontcg.io, 20,000 requests/day, but its ToS is silent on storing data in your own DB (no grant, no prohibition), its bulk-data repo PokemonTCG/pokemon-tcg-data has NO license (all-rights-reserved by default), access is terminable "at any time, with or without cause," and live keyless probes today returned HTTP 500 and 502 on two of three endpoints. Update cadence is comparable: TCGdex tags releases per set roughly every 1-2 months (v2.42.0 Fantastical Parade 2026-01-29 through v2.47.0 2026-07-18); pokemon-tcg-data commits a new set roughly every 2 months (me5 on 2026-07-17).

RECOMMENDATION: Use TCGdex, vendored — not queried live. Pin a cards-database release tag (currently v2.47.0) or run the tcgdex/server Docker image (multi-arch, linux/arm64 confirmed) beside the batch worker on the Pi, and run the entire ~91,570-card backfill against the local copy: zero external requests, which is strictly politer than even the 218 per-set API calls the public endpoint would happily absorb. Incremental enrichment of newly discovered cards then becomes 'bump the pinned tag when TCGdex cuts a set release' (every 1-2 months, matching PriceCharting's own new-set cadence) rather than an ongoing API dependency. Compliance is one line: keep TCGdex's MIT copyright/permission notice in the repo and credit TCGdex in docs; permanent Postgres storage, modification, and even future commercialization (D-034) are expressly covered by the MIT grant. The enrichment fields map directly: localId → card number, set.cardCount.official → printed size (with total > official flagging secret cards like 215/203), dexId → species. Treat pokemontcg.io as at most a manual cross-check: its ToS grants no storage right, its bulk dump is unlicensed, its access is revocable at will, and it was returning 500/502 during testing — a permanent enrichment column should not be built on it.

RISKS:
 - Neither source can license the underlying Pokemon IP (card names, characters, images) — TCGdex's MIT covers only their compilation, and both projects carry the same 'not affiliated with Nintendo/The Pokemon Company' disclaimer this project already uses. Storing facts (card number, set size, species name) is the lowest-IP-risk slice; storing card images would be a different question.
 - pokemontcg.io grants no explicit right to store its data: the ToS is silent, the bulk repo is unlicensed (all-rights-reserved by default under copyright law), terms are modifiable at any time, and access is terminable without cause — permanent Postgres storage rests entirely on implied license, which is weak footing for a permanent enrichment.
 - TCGdex data is community-maintained under an AS-IS MIT warranty disclaimer; its own FAQ acknowledges missing cards, wrong localIds, and known marketplace-ID mapping errors. Enriched values should carry provenance (source + version tag) so bad joins are auditable, consistent with this project's never-compute-on-insufficient-data rule.
 - Coverage is unverified: TCGdex has 218 English sets vs PriceCharting's ~303 sets (which include Japanese sets and promos). TCGdex claims 10+ languages including Japanese, but how many of the 91,570 PriceCharting cards actually match a TCGdex record was not measured here — that is the join-quality question, separate from licensing.
 - Two README quotes (the MIT statement and the Dockerfile sentence) were relayed through WebFetch's summarizer model rather than fetched raw; the LICENSE file itself, the FAQ, both pokemontcg.io docs pages, and the ToS were fetched raw. The README quotes are consistent with the raw LICENSE but are one step less direct.
 - pokemontcg.io showed live instability (HTTP 500/502 on 2 of 3 endpoints during probes) — any pipeline depending on it needs retry/backoff and should not be the primary path.
 - TCGdex's 'no hard rate limits' is a courtesy policy, not a contract — it could add limits at any time. Self-hosting/vendoring eliminates this exposure entirely, which is another argument for the vendored path.
